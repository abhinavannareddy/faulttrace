# J1939 support

Trucks, buses and construction machines report faults on the CAN bus using SAE J1939. A fault is an
**SPN** (which signal) plus an **FMI** (how it failed), carried in the DM1 message, which an ECU repeats
about once a second while a fault is active. FaultTrace decodes DM1 payloads and diagnoses them like any
other code set.

## What is decoded

A reassembled DM1 payload is two lamp bytes followed by four bytes per fault:

| Byte | Content |
|---|---|
| 1 | SPN bits 7..0 |
| 2 | SPN bits 15..8 |
| 3 | bits 7..5: SPN bits 18..16; bits 4..0: FMI |
| 4 | bit 7: conversion method (CM); bits 6..0: occurrence count |

The layout matches two independent sources (the python-can-j1939 decoder and a manufacturer's DM1
specification) and a round-trip test covers the three high SPN bits. The official standard is
paywalled and was not consulted; check this against your copy of SAE J1939-73 before relying on it.

- **No active faults** (SPN 0, FMI 0) and `FF FF FF FF` padding produce no fault.
- **Repeats**: because a DM1 is repeated while the fault stays active, only the first appearance of
  each SPN/FMI is used. That timestamp is when the fault appeared, which is what the burst analysis needs.
- **Legacy conversion methods** (CM = 1) are not decoded. The bytes alone do not say which legacy layout
  applies, so those faults are returned in `skipped_frames` with the reason.
- **Lamp bytes** are ignored; they do not change which component failed.
- **Transport**: the caller supplies reassembled payloads. A DM1 with several faults travels over the
  J1939 transport protocol, and FaultTrace does not reassemble CAN frames itself. Most loggers and
  gateways already do this.

## Using it

API: `POST /diagnose/j1939` with `{"vehicle": ..., "frames": [{"time_ms": ..., "data": "<hex>"}]}`.

CLI, with a CSV log of `time_ms,hex payload` per line (`#` starts a comment):

```text
# time_ms,payload
3000,00ff6e000305
3040,00ffa8000401
```

```bash
python -m faulttrace diagnose truck_j1939 --dm1-log capture.csv
```

Python:

```python
from faulttrace.j1939 import events_from_frames
from faulttrace.agents import diagnose
from faulttrace.model import load_vehicle

events, skipped = events_from_frames([{"time_ms": 3000, "data": "00ff6e000305"}])
report = diagnose(load_vehicle("truck_j1939"), events)
```

## Mapping your signals

Codes are matched as the string `SPN<n>-FMI<m>`. In a vehicle config, list each pair under `dtcs:` with
the component that owns it:

```yaml
dtcs:
  - {code: SPN110-FMI3, component: coolant_sensor, description: coolant temperature, voltage high}
  - {code: SPN168-FMI4, component: battery, description: battery potential low}
```

The mapping from signal to physical component is **the customer's knowledge**. It comes from the OEM's
diagnostic documentation, not from the SPN list, because the same SPN can be raised by different
components on different machines. A pair that is not in the config is returned in `codes_unknown`.

## The shipped example

`config/vehicles/truck_j1939.yaml` reuses the synthetic truck topology with J1939 codes. The SPN numbers
are real parameter numbers, checked against published parameter lists:

| SPN | Parameter |
|---|---|
| 84 | Wheel-based vehicle speed |
| 94 | Engine fuel delivery pressure |
| 102 | Engine intake manifold #1 pressure |
| 110 | Engine coolant temperature |
| 132 | Engine intake air mass flow rate |
| 157 | Injector metering rail pressure |
| 168 | Battery potential / power input 1 |
| 177 | Transmission oil temperature |
| 521 | Brake pedal position |
| 563 | Anti-lock braking (ABS) active |
| 639 | J1939 network #1 (primary vehicle network) |
| 3216 | Aftertreatment 1 intake NOx |

Which component raises which pair, and the FMI chosen for it, is an illustration for the synthetic
topology and no more. The descriptions deliberately do not spell out what each FMI means, because sources
word the FMI list differently, and the FMI value does not influence the diagnosis: the code string is just
an identifier. Replace the file with the mapping for your own machine.
