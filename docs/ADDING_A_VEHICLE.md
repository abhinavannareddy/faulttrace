# Adding a vehicle

A vehicle is one YAML file in `config/vehicles/`. Nothing in the Python code needs to change, and
the API lists the new vehicle automatically.

```yaml
vehicle: tractor                # display name, also used to seed the simulation
components:
  - {id: battery,    system: power}
  - {id: power_dist, system: power}
  - {id: engine_ecu, system: powertrain}
  - {id: hydraulics, system: hydraulics}
edges:                          # "a fault in `from` can make `to` misbehave"
  - {from: battery,    to: power_dist, p: 0.9}
  - {from: power_dist, to: engine_ecu, p: 0.9}
  - {from: engine_ecu, to: hydraulics, p: 0.8}
dtcs:                           # components not listed here are silent
  - {code: P0601, component: engine_ecu, description: engine ecu fault or out-of-range}
  - {code: P2501, component: hydraulics, description: hydraulic pressure low}
```

## Optional: priors and repair data

Per component, two optional fields make the output more useful for a real customer:

```yaml
components:
  - id: fuel_pump
    system: fuel
    failure_rate: 3.0          # relative to the other components; default 1.0
    service:
      action: Test supply pressure; inspect the relay and connector
      minutes: 35              # drives the order of the inspection plan
      part: "FP-2231"          # shown in the plan when present
```

- `failure_rate` is a prior: a component that fails three times as often is three times as likely a priori. Only
  ratios matter. Use warranty or fleet history; on synthetic incidents with uneven rates, configuring them
  raised top-1 accuracy from 72.6% to 80.3%. Wrong rates will mislead the ranking, so leave it out if you do
  not have data.
- `service` feeds the inspection plan, which orders checks by probability per minute. Without it each check is
  assumed to take 30 minutes and uses a generic action.

## What the loader checks

`load_vehicle` raises a `ValueError` naming the file and the offending entry when:

- a component id appears twice,
- an edge refers to a component that is not defined (this catches typos in `from` and `to`),
- an edge probability is outside (0, 1],
- a code belongs to a component that is not defined, or the same code is listed twice,
- a `failure_rate` is not positive.

These cases are covered by tests. Before the checks existed, a typo in an edge silently created an
extra component.

## Modelling advice

- Several codes can belong to one component. A component with no code is silent, which is how you
  model parts that fail without reporting: harnesses, relays, distribution units.
- Cycles are allowed. The simulator visits each component at most once per run.
- `p` is the chance that a fault passes along that link. Use lower values for weak dependencies. If
  you have FMEA or warranty data, this is where it goes.
- The shipped configs use the OBD-II format (a letter from P, C, B or U followed by four digits)
  and a test enforces it for them. Your own file may use any unique strings. For heavy-duty vehicles use the
  J1939 form `SPN3216-FMI4` ([J1939.md](J1939.md)).

## Checking the result

```bash
python -c "from faulttrace.model import load_vehicle as l; v = l('config/vehicles/tractor.yaml'); print(len(v.components), 'components,', len(v.dtc_component), 'codes')"
```

To measure accuracy, add the vehicle name to `VEHICLES` in `faulttrace/evaluate.py` and run
`python tools/analyze_errors.py`.

A silent component with exactly one downstream neighbour that has a code will be confused with that
neighbour (see [ERROR_ANALYSIS.md](ERROR_ANALYSIS.md)). That is a property of the graph you wrote,
not a bug.

The five shipped files are generated by `tools/make_configs.py`. Do not edit them by hand, because
they will be overwritten the next time the generator runs. A vehicle you add yourself lives only in
its own YAML file.
